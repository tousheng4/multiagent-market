# 撮合引擎优化建议

## 订单簿与撮合核心

- **价位队列结构**（`src/market/models/orderbook.py`）：当前价位下的订单使用 `list` 并在撮合中频繁 `pop(0)`，在高频场景下会带来大量移动开销。可改用 `collections.deque` 或自定义 FIFO 队列，删除表头即为 `O(1)`，同时可以直接存储挂单时间戳，强化“价格优先、时间优先”的撮合规则。
- **价格离散化**：在进入订单簿前先按品种最小 tick 将浮点价格转换为整数 tick（如 `ticks = round(price / tick_size)`），内部的 `SortedDict`/平衡树/桶都以 tick 为 key，可彻底规避浮点误差导致的“幽灵价位”，同时减少价位节点数。在对外展示或结算时再按 `price = ticks * tick_size` 还原即可。
- **价位树 + 订单链表**：将买卖两侧价位改为平衡树（例如 `SortedDict`、AVL、红黑树），树节点维护单价与聚合量，节点内部以双向链表串起同价位订单。这样可以 `O(log n)` 定位价位、`O(1)` 插入/删除头尾订单，撤单时只需节点引用即可在 `O(1)` 时间把订单从链表摘除，极大减轻高频挂撤场景的 GC 和移动开销。
- **价位清理与循环**（同文件 134-190 行）：撮合循环会不断检查空价位后才删除，若高并发撤单/挂单，会产生不少无效遍历。建议在下单/撤单阶段就即时维护一个“活动价位”计数，并在价位为空时立即移除，撮合循环即可直接跳过大部分逻辑。
- **聚合深度缓存**（`estimateFillCost` 部分）：估算成交成本时会对每档反复 `sum(order.remainingQuantity)`，时间复杂度随挂单数线性增长。可以在价位对象上维护 `total_qty`，在订单增删或撮合后更新，从而在估值时快速消费聚合量。

## 交易所与风控

- **风险检查扩展**（`src/market/models/exchange.py:_riskCheck`）：目前仅检查现金和持仓，缺少价格保护、动态保证金和撮合后余额校验。生产系统中建议加入：限价保护（防穿价）、保证金/杠杆规则、撮合后再执行一次余额验证并在失败时回滚。
- **限流与幂等**（`submitOrder` 入口）：没有速率限制、重复订单检测或熔断机制。可在 Agent 维度维护近期下单计数、挂单总量及重复请求 ID，超过阈值时拒单或降速，避免单个策略拖垮撮合服务。
- **审计与落库**（`_settleTrade`）：只更新内存状态，没有持久化或事件日志。应在成交后写入可靠消息（如 Kafka）或数据库，并确保持久化与余额更新具备事务性，以满足合规审计和容灾需求。

## 系统工程与可观测性

- **线程安全/并发模型**：`Exchange` 与 `OrderBook` 未加锁，若多个线程同时提交订单将出现竞态。可以把撮合放入单线程事件循环，其他线程通过队列提交；或为关键操作加读写锁并保证原子性。
- **日志与指标**：目前关键路径仅 `print`（例如 `src/environment/simulation.py` 中的数据事件）。需要统一接入结构化日志与监控指标（撮合延迟、订单拒绝率、成交量、撮合失败数等），便于上线观察与告警。
- **模块化拆分**：建议将撮合、行情广播、清算结算拆成独立组件，通过事件总线通信，既便于水平扩展，也能在不同进程/机器上部署，提高高可用性与容错能力。
